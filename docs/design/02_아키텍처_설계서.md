## 2. 레이어 규칙

| 레이어 | 파일 | 책임 | 규칙 |
|---|---|---|---|
| 진입 | `main.py` | 앱 생성, 라우터 등록, **기동 시퀀스** | 아래 3절 |
| 라우팅 | `app/routes.py` | HTTP 입출력, 검증, 오류 → JSON | **비즈니스 로직을 두지 않는다** |
| 도메인 | `app/{select_ai,vector_search,duality,graph,productivity,awr_analyzer_v2}.py` | SQL 작성·실행, 결과 가공 | 서로 import 하지 않는다 |
| 인프라 | `app/{database,llm_client,config,scheduler}.py` | 커넥션 풀, LLM 어댑터, 설정, 스케줄 | 도메인을 모른다 |

> **현재 `routes.py` 가 1,450줄로 비대하다.** SPA 이식(Phase 5) 때 탭 단위로
> `app/routers/{nl2sql,vector,duality,graph,productivity,awr}.py` 로 쪼갠다.
> 탭 하나를 옮길 때 그 라우터를 함께 잘라내는 방식이라 별도의 대규모 리팩터링 세션이 필요 없다.

## 3. 기동 시퀀스 (`main.py: startup`)

```
1. init_pool()                      DB 커넥션 풀 (min1/max5, call_timeout 120s)
2. init_vector_tables(pool)         DOCUMENTS/DOC_CHUNKS + HNSW 인덱스 없으면 생성
3. asyncio.create_task(warm_...)    ★ 커넥션 풀 워밍 — 백그라운드
4. init_scheduler()                 ADB Keepalive (주 1회 월 09:00)
   → "Application startup complete"  (워밍보다 먼저 뜬다)
   → ~15초 뒤 "✓ 커넥션 풀 워밍 완료: 5/5개"
```

### ★ 왜 커넥션 풀 워밍이 필요한가

DB 내장 ONNX 임베딩은 **커넥션마다 모델을 최초 1회 로드**하며 비용이 크다
(E5_BASE 5.2초 / E5_SMALL 1.1초, 2회차부터 20~40ms). 풀이 max=5 라 데모 도중
새 커넥션이 배정될 때마다 5초짜리 멈춤이 산발적으로 나타났다.

`warm_embedding_pool()` 은 커넥션 5개를 **동시에** 잡아 각각 임베딩 1회를 돌린다.
순차로 acquire/release 하면 같은 커넥션이 재사용되어 하나만 달궈진다.
서버 기동을 막지 않도록 백그라운드 태스크로 돌린다.

## 4. 데이터 흐름 — 세 가지 패턴

### (a) 단순 요청/응답 (대부분)
```
브라우저 fetch → routes.py → 도메인 모듈 → pool.acquire() → SQL → 결과 가공 → JSON
```

### (b) SSE 스트리밍 (PDF 업로드 · AWR 분석)
```
브라우저 fetch + ReadableStream
   ↓
StreamingResponse(text/event-stream)
   ↓  event: step   {step, label, status, duration_ms}
   ↓  event: progress {current, total, percent}
   ↓  event: done   {success, ..., pipeline[]}
```
진행률을 **청크 단위**로 흘려보낸다. 실패해도 본문은 저장하되,
**실패 건수와 첫 오류를 `done` 이벤트에 실어 보낸다**(2026-09-04 신설 —
그전에는 임베딩이 전부 실패해도 "79개 완료"로 보고했다).

### (c) 외부 LLM 호출 (RAG 답변 · AWR 분석)
```
검색 결과 청크 → 프롬프트 조립 → llm_client.call_llm() → Groq 또는 Gemini
```
`llm_client.py` 가 어댑터다. 라우터·도메인은 구체 제공자를 직접 참조하지 않는다.

## 5. 벡터 검색 파이프라인

```
PDF ─pdfplumber─▶ 페이지 텍스트
      │
      ├─ DBMS_VECTOR_CHAIN.UTL_TO_CHUNKS  (실패 시 Python 청킹 500자/50 overlap)
      │
      └─▶ 청크 ──VECTOR_EMBEDDING(ONNX) 또는 외부 API──▶ 768차원 벡터
                    │
                    └─▶ INSERT doc_chunks (embedding)
                            ├─ HNSW 인덱스 자동 반영
                            └─ Oracle Text 인덱스 SYNC(ON COMMIT) 자동 반영
```

검색 시 4가지 모드가 같은 테이블을 다르게 읽는다 —
`vector`(VECTOR_DISTANCE) / `keyword`(CONTAINS+SCORE) /
`hybrid`(둘을 LEFT JOIN 으로 결합) / `compare`(양쪽 동시 실행).

## 6. 성능상 반드시 지킬 것

| 규칙 | 근거 (2026-09-04 실측) |
|---|---|
| `VECTOR_EMBEDDING` 은 **항상 `(SELECT ... FROM dual)` 스칼라 서브쿼리**로 | 인라인이면 행마다 재평가 — 11.3초 vs 0.11초 (**100배**) |
| 기동 시 **커넥션 풀 워밍** | 콜드스타트 5.2초/커넥션 제거 |
| Oracle Text 인덱스 유지 | `CONTAINS` 104ms vs `LIKE` 9,880ms (**95배**) |
| 자연어 질의는 **ACCUM 변환** 후 CONTAINS | 문장 직접 전달 시 `ORA-29902` → 하이브리드가 벡터 전용으로 퇴화 |
| `pool.acquire()` 안에서 느린 await 금지 | LLM·외부 API 호출은 커넥션 반납 후 |
