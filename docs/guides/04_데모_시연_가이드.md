# 데모 시연 가이드

> **이 문서는 앱 「매뉴얼」 탭에서도 열립니다.**
> 최종 갱신: 2026-09-04 · 대상: 이 앱으로 Oracle 26ai 를 시연하는 사람

---

## 1. 시연 전 체크리스트 (T-10분)

```bash
# ① 상태 확인
curl -s http://localhost:8247/api/health | python3 -m json.tool
```

| 확인 | 정상값 | 아니면 |
|---|---|---|
| `database_connected` | `true` | 트러블슈팅 2절 |
| `profile_count` | `≥ 1` | Select AI 시연 불가 |
| `chunk_count` / `embedded_count` | **둘 다 > 0, 같은 값** | PDF 를 미리 업로드 |
| `onnx_models` | 비어 있지 않음 | ONNX 시연 불가 |

```bash
# ② 그래프·Duality 준비 (없으면 시연 중에 만들어도 되지만 미리 해두면 매끄럽다)
curl -s -X POST localhost:8247/api/graph/create
curl -s -X POST localhost:8247/api/duality/create-views
```

**③ 재기동했다면 15초 기다립니다.** 로그에 `✓ 커넥션 풀 워밍 완료` 가 뜬 뒤 시작하세요.
안 그러면 첫 벡터 질의에서 5초 침묵이 생깁니다.

**④ 브라우저 탭을 미리 열어 각 탭을 한 번씩 눌러둡니다.** 첫 진입 로딩이 사라집니다.

## 2. 15분 표준 시연 시나리오

시간이 빠듯하면 **②번(Vector Search)과 ④번(Property Graph)만** 하세요. 반응이 가장 좋습니다.

### 여는 말 (30초)

> "Oracle 26ai 는 AI 기능을 **DB 밖으로 데이터를 내보내지 않고** DB 안에서 처리합니다.
> 오늘은 그걸 슬라이드가 아니라 **실제 SQL 과 실행 결과로** 보여드리겠습니다.
> 모든 탭이 같은 구조입니다 — **같은 질문을 두 방식으로 풀어 나란히 놓고 비교**합니다."

### ① NL2SQL (3분)

| 순서 | 조작 | 말할 것 |
|---|---|---|
| 1 | 프로필 `GROQ_SH_PROFILE` 선택 | "LLM 이 앱이 아니라 **DB 안에서** 호출됩니다" |
| 2 | 모드 `SQL 보기`, 예시 질문 선택 → 질문 | "자연어가 SQL 이 됐습니다" |
| 3 | 모드 `프롬프트` 로 바꿔 재질문 | **"DB 가 LLM 에 뭘 보냈는지 그대로 보여드립니다"** ← 반응이 좋은 지점 |
| 4 | 모드 `SQL 실행` | 실제 결과표 |

> **한 방**: `showprompt`. 블랙박스가 아니라는 걸 보여줍니다.

### ② AI Vector Search (5분) — **하이라이트**

| 순서 | 조작 | 말할 것 |
|---|---|---|
| 1 | Vector Store 관리 → 테이블 정의 | "`embedding VECTOR` 컬럼. 벡터가 **테이블 안에** 있습니다" |
| 2 | 검색 → **비교 모드**로 질문 | **좌우 결과가 다릅니다.** "키워드는 단어가 같아야 찾고, 벡터는 뜻이 같으면 찾습니다" |
| 3 | 같은 질문을 **하이브리드**로 | "26ai 는 이 둘을 **하나의 SQL** 에서 합칩니다" |
| 4 | 참조 청크 펼치기 | `vector`·`keyword`·`hybrid` 점수 → "순위가 왜 이런지 숫자로 설명됩니다" |
| 5 | 실행 쿼리 확인 | **"방금 돈 SQL 원문입니다"** ← 신뢰도가 올라가는 지점 |

> **한 방**: 비교 모드의 좌우 차이. 질문은 **동의어를 쓰는 것**으로 고르세요
> (문서에 "인덱스 사용 지침"이 있다면 "인덱스를 효율적으로 쓰려면?" 처럼).
> 그래야 키워드가 못 찾고 벡터가 찾는 대비가 선명합니다.

### ③ JSON Relational Duality (2분)

| 순서 | 조작 | 말할 것 |
|---|---|---|
| 1 | 관계형 vs JSON 비교 | "같은 데이터의 두 얼굴입니다. **복제본이 아닙니다**" |
| 2 | 문서 조회 → JSON 수정 → 저장 | **"JSON 을 고쳤는데 관계형 테이블이 바뀝니다"** |
| 3 | ETag 동시성 제어 | "동시 수정은 ETag 로 막습니다" |

> **한 방**: 2번. "앱 개발자는 JSON 을, DBA 는 테이블을 원합니다. 보통은 동기화 코드를
> 짜는데, 여기선 **같은 데이터**라 동기화가 필요 없습니다."

### ④ Property Graph (3분)

| 순서 | 조작 | 말할 것 |
|---|---|---|
| 1 | 그래프 생성 | **"기존 테이블 위의 뷰입니다. 데이터를 옮겨 담지 않습니다"** |
| 2 | SQL vs SQL/PGQ 비교 → **3번 쿼리** | "같은 답인데 표현이 다릅니다" |
| 3 | PGQ 쿼리 문장 짚기 | `(c1)-[s1]->(p)<-[s2]-(c2)` → **"추천 시스템의 원리가 한 줄입니다"** |

> **한 방**: 1번의 "데이터 복제 없음". 전용 그래프 DB 와의 결정적 차이이고,
> DBA 청중이 가장 크게 반응하는 지점입니다.

### ⑤ 개발생산성 · ⑥ AWR (각 1분, 시간 남으면)

- **Lock-Free Reservations**: "동시 차감에서 잠금 대기가 사라집니다"
- **AWR 분석**: 미리 분석해 둔 결과 탭을 보여주세요. **현장에서 업로드하면 수십 초 걸립니다**

## 3. 자주 나오는 질문

| 질문 | 답 |
|---|---|
| "데이터가 외부로 나가나요?" | 임베딩은 **DB 내장 ONNX** 라 안 나갑니다. LLM 답변 생성만 외부 API 를 씁니다(교체 가능) |
| "벡터 검색이 얼마나 빠른가요?" | 79청크 기준 **95ms**. HNSW 인덱스를 씁니다 |
| "전체가 3~4초던데?" | 대부분 **LLM 답변 생성** 시간입니다. 비교 모드(RAG 없음)로 보면 40~70ms |
| "Neo4j 랑 뭐가 다른가요?" | **데이터 복제가 없습니다.** 기존 테이블 위의 뷰라 ETL·동기화가 필요 없습니다 |
| "이 SQL 진짜인가요?" | 「실행 쿼리 확인」을 누르세요. `V$SQL` 에서 방금 돈 원문이 나옵니다 |
| "얼마나 큰 문서까지?" | 업로드 10MB, AWR 20MB. 27쪽 PDF 가 79청크·30초 |
| "정확도가 어느 정도?" | 유사도 점수가 화면에 나옵니다. Annotation 을 붙이면 NL2SQL 정확도가 올라갑니다 |

## 4. 하지 말 것

| 함정 | 왜 |
|---|---|
| **재기동 직후 바로 시작** | 워밍 전이라 첫 벡터 질의에서 5초 침묵 |
| **현장에서 임베딩 모델 바꾸기** | 차원이 다르면 이후 업로드 임베딩이 저장되지 않습니다(HNSW 차원 고정) |
| **현장에서 큰 PDF 업로드** | 27쪽이 30초입니다. 미리 올려두고 파이프라인만 짧은 문서로 시연 |
| **현장에서 AWR 분석 실행** | 파싱+LLM 이 수십 초. 결과 탭을 미리 만들어 두세요 |
| **키워드 모드로 자연어 문장 질문** | 질의어가 불용어뿐이면 0건이 나옵니다. 키워드 모드는 **명사 위주**로 |
| **`WITH` 로 시작하는 SQL 직접 실행** | SELECT 로 시작하는 문장만 허용됩니다 |

## 5. 시연이 꼬였을 때

| 상황 | 즉시 조치 |
|---|---|
| 화면이 멎은 것 같다 | 5초 기다립니다. 워밍이나 LLM 호출일 가능성이 높습니다 |
| 검색이 0건 | **비교 모드**로 전환 — 최소한 벡터 쪽은 나옵니다 |
| NL2SQL 이 500 | 사이드바에서 **다른 프로필로 전환**(외부 LLM 한도일 가능성) |
| 그래프 쿼리 오류 | 그래프 삭제 → 재생성 |
| 전부 이상 | `/api/health` 를 화면에 띄워 상태를 보여주며 시간을 버세요 — 그 자체로 설명거리가 됩니다 |

> **모르는 것을 아는 척하지 마세요.** 이 앱은 문서가 앱 안에 있습니다 —
> 「매뉴얼」 탭을 열어 함께 보는 것도 좋은 대응입니다.
