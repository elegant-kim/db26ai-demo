## 0. 이 계획서의 목적과 설계 원칙

### 0.1 왜 이 계획서가 필요한가 — 이번에 실제로 겪은 문제

2026년 4월에 멈춘 이 프로젝트를 9월에 다시 열었을 때, **개발자 본인이 `docs/41`·`42` SQL 파일이
무엇이었는지 기억하지 못했다.** 코드도 커밋 메시지도 남아 있었지만, "지금 이 앱이 어떤 상태인가"에
답하는 문서가 없었기 때문이다. 결국 앱을 실행해 DB에 직접 질의해서야 이관이 완료됐음을 확인했다.

이 계획서의 **최우선 목표는 기능 추가가 아니라, 그 상황이 다시 오지 않게 만드는 것**이다.
5개월 뒤에 열어도 사람과 Claude 둘 다 문서만으로 현재 상태를 파악할 수 있어야 한다.

### 0.2 설계 원칙 5가지

| # | 원칙 | 이유 |
|---|---|---|
| P1 | **문서는 git 안에, 코드와 같은 커밋에** | 코드만 커밋하고 문서를 미루면 반드시 어긋난다 (investhub 실측: 퀵가이드가 3일 뒤에야 따라잡음) |
| P2 | **정본은 한 곳에만** | 두 곳에 적으면 반드시 어긋난다 (investhub 실측: 주석의 탭 순서가 실제와 달랐음) |
| P3 | **사람이 읽을 문서는 앱 메뉴에서도 열려야 한다** | 소스 폴더를 뒤지지 않아도 되게. 데모 현장에서도 열람 가능 |
| P4 | **"수정했다"가 아니라 "검증했다"가 완료 기준** | 현재 이 저장소는 테스트가 0건이라 검증 자체가 불가능하다 |
| P5 | **되돌릴 수 없는 것만 확인을 구한다** | 조회·빌드·테스트·문서·배포는 확인 없이 진행 (마찰 감소) |

### 0.3 완성 시 도달할 문서 체계 (4층)

| 층 | 파일 | 독자 | 로드 방식 | 답하는 질문 |
|---|---|---|---|---|
| **L1** | `CLAUDE.md` | Claude + 사람 | 매 세션 자동 | 이 앱은 무엇이고, 어떤 규칙으로 만드나 |
| **L2** | `docs/개발노하우.md` | Claude | `@import`로 자동 | 어떻게 일하나 — 작업 규율·검증 사이클·반복 함정 |
| **L3** | `docs/SESSION_HANDOFF.md` | Claude + 사람 | 세션 시작 시 수동 | **지금 상태가 어떤가 / 마지막에 뭘 했나 / 뭐가 미완인가** |
| **L4** | `docs/guides/NN_*.md` + 기능 레지스트리 | **사람** | **앱 메뉴 → 매뉴얼 탭** | 어떤 기능이 어디 있고, 언제 쓰나 |

> **L3가 이번 "기억 안 남" 문제의 정면 해법이다.** investhub의 `docs/SESSION_HANDOFF.md`(72줄)가
> 검증된 원형이고, 여기에 "**현재 환경 실측 스냅샷**"(DB 접속 대상·데이터 적재 상태·미완 작업)을
> 추가해 db26ai-demo용으로 강화한다.

### 4.2 정직하게 덧붙이는 단서

- **Opus 5도 UI를 못 만들지 않는다.** Fable의 이득은 실재하지만 *증분*이다. 사용자 표현대로
  *"Opus로도 할 수 있지만 Fable이 조금 더 잘 하는 부분"* 이 정확한 인식이다.
- **모델보다 큰 지렛대는 4-2의 방법이다** — investhub를 실제로 띄워 캡처한 기준선이 있으면
  Opus로도 충실도가 크게 오르고, 기준선이 없으면 Fable로도 "느낌만 비슷한" 결과가 나온다.
- **5-1 실측 후 재조정한다.** 첫 탭 결과를 보고 5-2·5-3을 Fable로 올릴지, 반대로 5-4·5-5를
  Opus로 내릴지 판단한다. 지금 배분은 착수 전 추정이다.
- **Fable 프롬프트 주의:** 지시를 잘게 못 박을수록 결과가 나빠진다. 목표·제약·기준선만 주고
  판단을 맡길 것. Opus에 맞춰 쓰던 상세 지시문을 그대로 쓰면 오히려 손해다.
