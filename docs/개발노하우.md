## 1. 작업 규율

- 여러 단계가 필요한 작업은 시작 전에 계획하고, 단계마다 결과를 검증한 뒤 다음으로 간다.
- 시작한 작업은 끝까지 완료한다. **"수정했다"가 아니라 검증된 코드가 완료 기준**이다.
  계획만 말하고 멈추지 않는다.
- 막히면 조용히 넘어가지 말고 보고한다: 지금까지 결과 + 막힌 지점 + 시도 + 대안.
- 모호한 요청은 가장 그럴듯한 해석을 명시하고 진행한다. 해석이 크게 갈릴 때만 질문하고,
  질문은 한 번에 하나만.

### 코드 수정
- 수정 전에 대상 파일을 실제로 읽는다. 읽지 않은 파일을 고치지 않는다.
- **요청된 범위만** 고친다. 요청 없는 리팩터링·기능추가·스타일변경은 완료 후 "제안"만 한다.
  (단, 사용자가 "전체 점검"·"최적화 확인" 등 넓은 범위를 명시하면 그게 곧 요청 범위다.)
  범위를 넘는 판단을 했다면 **넘었다는 사실을 명시**하고 되돌리기 쉬운 형태로 남긴다.
- 존재하지 않는 API·함수·라이브러리를 추측으로 쓰지 않는다. 실제 코드·타입·문서로 확인하고,
  확인 못 했으면 그 사실을 밝힌다.
- 수정 후 검증한다: 테스트/빌드, 없으면 최소 구문·타입 체크 + 실제 호출.
- 기존 코드 스타일·컨벤션을 따른다. 내 취향으로 바꾸지 않는다.

### 불확실성·정직
- 확신 없는 정보(라이브러리 동작, 버전차, 설정 효과)는 사실처럼 쓰지 않는다.
  코드·문서로 확인하거나 "확실하지 않다"고 밝힌다.
- **측정값을 인용할 때는 측정 조건을 함께 말한다.** 2026-09-04 실측: ONNX 임베딩 속도를
  콜드스타트 포함 값으로 비교해 "E5_SMALL이 6배 빠르다(17분 vs 2.7분)"고 보고했는데,
  워밍 상태 실측은 14ms 대 44ms(79청크 1.2초 대 3.5초)였다. **조건을 빠뜨린 수치는 오도한다.**
- 사용자가 오류를 지적하면 먼저 사실을 확인한다. 맞으면 간결히 인정·수정, 틀린 지적이면
  근거를 들어 정중히 기존 판단을 유지한다.
- 내 이전 작업의 오류는 지적받기 전에 먼저 정정한다.

## 2. 운영·검증 워크플로우 (db26ai-demo 고유)

**작업 분담**: DDL·데이터 갱신은 **Claude가 직접 수행**하고, 사용자는 화면 결과만 확인한다.
셋업 SQL 실행과 `launchctl` 재기동은 **표준 작업 사이클의 일부**이므로 매번 확인을 구하지 않는다.

**변경 → 검증 → 배포 사이클** (관찰 가능한 변경일 때):
1. 검증: `./venv/bin/python -m pytest tests/ -q` + `./venv/bin/ruff check .`
   (서버가 안 떠 있으면 통합 테스트는 자동 skip 되고 단위 테스트만 돈다)
2. 운영 반영: `launchctl kickstart -k gui/$(id -u)/com.db26ai.server`
   — **백엔드는 자동 리로드가 없으므로 재기동 필수.** 기동 후 커넥션 풀 워밍에 ~15초가 더 걸린다.
3. 스모크: `curl -s localhost:8247/api/health` → 해당 탭의 대표 엔드포인트 호출
4. 스크립트·일회성 DB 작업은 **프로젝트 루트 cwd**에서 `./venv/bin/python`으로 실행(.env 로딩).
   `/api/execute-sql`은 SELECT 로 시작하는 문장만 받으므로 DDL·CTE는 스크립트로 돌린다.

**확인이 반드시 필요한 것** (이것만): 시크릿(.env·키·wallet) 수정, `git push --force`,
`DROP TABLE`/조건 없는 `DELETE` 등 되돌릴 수 없는 대량 삭제, 저장소 밖 파일 삭제.
그 외 조회·읽기·구문검사·DDL(인덱스·뷰·그래프)·시드·배포(launchctl)는 확인 없이 진행한다.

**커밋·푸시**: **검증이 끝난 변경은 묻지 말고 바로 커밋·푸시한다.**
작게 자주가 원칙 — 되돌리기가 정확해지고(문제 커밋 하나만 revert), 언제 깨졌는지 이분 탐색이
가능하며, 메시지가 곧 변경 이유의 기록이다.
- 논리 단위로 분리, 한글 명령형 메시지 + 끝에 `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`
- 커밋 메시지에 **왜 그랬는지와 실측 수치**를 남긴다. 이 저장소의 커밋이 곧 함정 기록이다.
- 여전히 확인을 구하는 것: `git push --force`, 여러 아크가 뒤섞여 분리 기준이 모호할 때.

## 3. 실측으로 확인된 반복 함정

기록 계기가 있었던 것만. 새 함정을 만나면 여기 한 줄 추가한다.

### 3.1 이 저장소에서 하루에 4번 재현된 것 — **`except: pass`는 실패를 숨긴다**

2026-09-04 하루에 **같은 원인의 버그 4건**을 찾았다. 전부 HTTP 200 을 반환하며 정상인 척했다.

| 증상 | 실제 원인 | 숨긴 코드 |
|---|---|---|
| `/api/health` 가 5개월간 `onnx_models: []` (실제로는 2개 존재) | `get_onnx_models()`는 list 인데 `.get("models")` 호출 → `AttributeError` | `except Exception: pass` |
| 업로드가 "79개 완료" 보고, 실제 임베딩은 **전량 NULL** | `ORA-51932` (HNSW 인덱스 384차원에 768차원 입력) | `except Exception:` 후 임베딩 없이 INSERT + 카운트는 +1 |
| 키워드 검색이 9.9초, 구(句) 질의 0건 | Oracle Text 인덱스 부재 → LIKE 폴백 | 폴백이 조용해서 아무도 몰랐다 |
| 하이브리드가 사실상 vector-only | 코드가 CONTAINS 를 아예 시도하지 않음 | CLAUDE.md 기술과 코드가 갈라져 있었다 |

**규칙**: 예외를 삼켜야 하는 자리라도 **`logger.warning`은 반드시 남긴다.**
그리고 **"성공 카운트"는 실제 성공분만 센다** — 폴백 경로에서 +1 하면 지표가 거짓말을 한다.
발화하지 않는 실패는 없는 실패와 같다.

### 3.2 Oracle 26ai 벡터·그래프

- **`VECTOR_EMBEDDING`을 쿼리에 인라인으로 두면 행마다 재평가된다 — 100배 차이**(2026-09-04):
  79청크 기준 hybrid 11.3초 / vector 5.4초. `(SELECT VECTOR_EMBEDDING(...) FROM dual)`
  스칼라 서브쿼리로 감싸면 0.1초 / 0.095초. **모든 벡터 쿼리에서 반드시 감쌀 것.**
- **`VECTOR_EMBEDDING` 모델명은 bind variable 불가**: SQL identifier 라서 `:model`로 넘기면
  silent failure. f-string 삽입 + `replace("'", "")` 이스케이프.
- **ONNX 모델은 커넥션마다 최초 1회 로드된다**(2026-09-04): E5_BASE 5.2초 / E5_SMALL 1.1초,
  2회차부터 20~40ms. 풀 max=5 라 데모 중 산발적 5초 멈춤이 생긴다 →
  `warm_embedding_pool()`이 기동 시 커넥션을 **동시에** 잡아 예열한다.
  순차 acquire/release 하면 같은 커넥션이 재사용되어 하나만 달궈진다.
- **임베딩 모델 교체 = HNSW 인덱스 재생성**(ORA-51932): `embedding VECTOR` 컬럼은 차원
  무제약이지만 인덱스가 첫 데이터의 차원으로 고정된다. 순서: 청크 삭제 → `DROP INDEX
  doc_chunks_hnsw_idx` → 새 모델로 재적재 → 인덱스 재생성. **UI의 런타임 임베딩 전환도
  이 함정을 그대로 밟는다**(전환 후 업로드하면 임베딩이 전부 NULL 이 된다 — 미해결 부채).
- **VECTOR 컬럼에 집계함수 직접 사용 불가**(ORA-22849): `COUNT(embedding)` 실패.
  `COUNT(CASE WHEN embedding IS NOT NULL THEN 1 END)` 로 우회.
- **SQL/PGQ: `GRAPH_TABLE()`의 `COLUMNS` 절 안에서 집계 불가**(ORA-49011: A group function
  inside GRAPH_TABLE() must have a group reference). 원시 행을 투영하고 **바깥에서 집계**한다.
- **Oracle Text 인덱스의 렉서는 한글이면 `WORLD_LEXER`**: 기본 `BASIC_LEXER`는 공백 분리라
  "인덱스를"이 "인덱스"로 매칭되지 않는다. `SYNC (ON COMMIT)`이면 업로드 직후 검색 가능.
  `CONTAINS` 104ms vs `LIKE` 9,880ms — **95배**.
- **자연어 문장을 `CONTAINS` 에 그대로 넣으면 ORA-29902**(2026-09-04): `?` 등이 Oracle Text
  예약 연산자다. 그러면 LIKE 로 폴백되는데 문장 전체 LIKE 는 0건이라, **하이브리드가 이름만
  하이브리드고 실제로는 벡터 전용으로 퇴화**했다(참조 청크의 keyword 가 전부 0).
  → `to_contains_query()`가 ACCUM 구문으로 변환한다:
  `"인덱스를 효율적으로 … SQL을 작성해야 하나요?"` → `"인덱스%, 효율%, 사용%, SQL, 작성%"`.
  **AND 가 아니라 쉼표(ACCUM)를 쓴다** — 하이브리드의 키워드 성분은 필터가 아니라 점수라
  한 단어가 없다고 0건이 되면 안 된다. 영문+조사("SQL을")는 영문부만 남긴다(우측 절단하면
  "SQ%" 로 과매칭).
  **이 결함은 API 검증으로는 안 잡혔다** — 짧은 키워드로만 테스트했기 때문이다.
  화면에서 사람처럼 질문해 보고서야 드러났다(4절 참조).
- **`SCORE(n)`은 같은 문장 WHERE 에 `CONTAINS(...,n)`이 있어야 쓸 수 있다.** 그런데 WHERE 에
  두면 키워드 미매칭 행이 걸러져 하이브리드 의미가 깨진다 → **LEFT JOIN 서브쿼리로 분리**하고
  `NVL(k.kw_score, 0)`으로 채운다.

### 3.3 Oracle 일반

- **LOB 처리**: `hasattr(row[0], 'read')` 체크 후 `await _lob_to_str(val)` 변환 필수.
- **DDL에 bind variable 불가**: `ALTER TABLE ... ANNOTATIONS` 등은 문자열 포맷팅 +
  `replace("'", "''")` 이스케이프.
- **커넥션 풀 중첩 acquire 금지**: `pool.acquire()` 블록 안에서 또 커넥션을 잡으면 DPY-4005
  (풀 고갈). SELECT로 값을 받아 반납 → 처리 → 필요 시 재획득.
- **`pool.acquire()` 블록 안에서 느린 await 금지** (LLM 호출·외부 API·임베딩 루프):
  커넥션을 장기 점유해 다른 요청을 굶긴다.
- **VARCHAR2 기본은 BYTE 단위**: 한글은 UTF-8 3바이트라 `VARCHAR2(2000)`에 파이썬 `[:2000]`
  자르기로도 ORA-12899. 한글 텍스트 컬럼은 `VARCHAR2(N CHAR)`로 선언.
- **Oracle bind 이름에 `uid` 금지**(ORA-01745): `UID`는 예약 함수 → `:p_uid` 처럼 접두사.

### 3.4 도구·환경

- **`/api/execute-sql`은 SELECT 로 시작하는 문장만 받는다** — `WITH` CTE 도 거부된다.
  CTE·DDL·DML 을 돌려야 하면 `./venv/bin/python` 스크립트로 pool 을 직접 쓴다.
- **API 응답 구조가 엔드포인트마다 다르다**: 결과 배열 키가 `data`(execute-sql) /
  `chunks`(vector/search) / `sql_data`·`pgq_data`(graph/compare) / `models`(onnx).
  2026-09-04 세션에서 Claude 가 **3번** 잘못 읽었다. **응답을 파싱하기 전에 키를 먼저 확인한다**
  (`for k,v in d.items()` 로 덤프). SPA 이식 때 정규화 대상(부채 D11).
- **zsh 글로브**: `grep --include=*.py` 는 zsh 에서 `no matches found` 로 죽는다.
  대상 파일을 나열하거나 따옴표로 감싼다.
- **launchd 재기동 후 즉시 스모크하면 실패한다**: 기동 자체는 빠르지만 커넥션 풀 워밍이
  ~15초 걸린다. 워밍은 백그라운드라 서버는 먼저 응답하지만, 첫 벡터 질의는 워밍 완료 후가 정확하다.

## 4. UI·표현 원칙

현재 프론트는 단일 파일 3종(`index.html`·`app.js`·`style.css`, 8,338줄)이며
**Vue 3 + TypeScript + Vite SPA 로 이식 예정**이다(`docs/ROADMAP.md` Phase 4·5).
디자인 기준선은 자매 프로젝트 `~/Dev/investhub`의 `web/` 이다.

- UI 텍스트는 전부 한국어. 대상은 **Oracle 26ai 를 처음 접하는 개발자·DBA**.
- **프론트 파일을 고치면 `?v=N` 캐시버스팅 버전을 반드시 올린다.** 안 올리면 브라우저가
  옛 파일을 그대로 쓴다 — "고쳤는데 화면이 안 바뀐다"의 단골 원인.
- **`typecheck`·`build` 통과는 '동작 확인'이 아니다.** 화면을 실제로 열어보거나,
  못 열면 그 사실을 보고한다.
- **비동기 대기는 "멈춤"과 "작업 중"을 구분**해 보여준다. 특히 첫 벡터 질의(워밍 전)·
  PDF 업로드·AWR 분석은 수 초~수십 초가 걸린다. 진행률 SSE 를 화면에 반드시 반영한다.
- 이 앱의 핵심 서사는 **"같은 질문을 두 방식으로 풀어 나란히 비교"** 다
  (SQL vs PGQ, 키워드 vs 의미 검색, 관계형 vs JSON). **두 결과가 화면에서 실제로 비교
  가능해야 한다** — 정렬이 달라 다른 행이 뜨면 그 주장 자체가 무너진다(2026-09-04 실측 2건).
